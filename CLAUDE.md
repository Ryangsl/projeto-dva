# PROCAR — Guia de Atendimento

> Documento vivo. Fonte de verdade sobre o projeto: visão, arquitetura, decisões, estrutura e log de evolução. **Atualizar a cada mudança relevante** (nova feature, decisão de arquitetura, migration, etc.).

## 1. Visão do Produto

**O produto é um GUIA DE ATENDIMENTO — não um fichário de clientes.**

Durante o atendimento no balcão, o consultor informa **carro → modelo → cor** e o sistema mostra:
1. **Como conduzir o atendimento** — roteiro em etapas (acolhimento, diagnóstico, apresentação, benefício...) com **a frase sugerida de como falar com o cliente**, personalizada pelo veículo (ex.: *"Olá, seja muito bem-vindo à PROCAR! Que Nivus bonito. Posso te ajudar a deixar ele ainda mais protegido?"*).
2. **O que ofertar** — os **produtos/serviços recomendados** para aquele veículo (PPF, vitrificação, película, estética...) com o argumento de venda contextualizado pela cor/modelo.

O objetivo é **padronizar o atendimento e potencializar a venda de serviços**, transformando as regras que hoje vivem na ficha de papel em um roteiro guiado e dinâmico.

> ⚠️ **O que este sistema NÃO é:** não é um cadastro/arquivo de dados de clientes. Guardar dados de cliente/veículo é secundário (e opcional) — o valor está no guia. Métricas e histórico de atendimentos são fase futura (CRM), fora do escopo atual.

### Personas
- **Consultor**: no balcão, seleciona o veículo e segue o guia (fala + ofertas).
- **Gestor**: administra os usuários (Consultores) da(s) própria(s) loja(s) — pode administrar **mais de uma concessionária** — cria, edita, desativa e reseta senha — e acompanha o monitoramento de uso; manter o conteúdo do guia (produtos, roteiro e regras) é fase P3.
- **Admin (TI)**: gerencia todos os usuários do sistema (qualquer loja/perfil, incluindo criar Gestores). Assim como os demais perfis, passa pelo **primeiro acesso obrigatório** e pode trocar a própria senha em "Minha senha" — não há mais caminho de senha via SQL.

## 2. Requisitos Não-Funcionais (críticos)

- **Leveza / baixa dependência de internet.** A internet do local é ruim. O sistema deve funcionar com o mínimo de tráfego de rede:
  - O conteúdo do guia (fabricantes, modelos, cores, serviços, roteiro e regras) é **pequeno e carregado de uma vez**, então **cacheado no cliente** (localStorage). Após o primeiro carregamento, selecionar veículo e ver o guia **não faz novas chamadas de rede**.
  - A avaliação das regras (que serviços/frases mostrar) acontece **no frontend**, sobre os dados já em cache — zero round-trips durante o atendimento.
  - Bundle enxuto; evitar dependências pesadas.
- **Mobile First com foco em tablet** (usado no balcão) → adapta para celular, notebook e desktop.
- **Sem integrações externas no caminho crítico.** Os dados de veículos vêm da **FIPE**, mas **já importados para o MySQL** (tabelas `vehicle_*`) — o app **não chama a API FIPE em tempo de atendimento**. Para manter leve e relevante, o guia usa apenas as **marcas principais** (lista configurável).

## 3. Stack Técnica (obrigatória)

| Camada | Tecnologia |
|---|---|
| Frontend | React 18 + TypeScript (Vite), mobile-first |
| Backend / API | Node.js + Express (REST) |
| Banco de Dados | MySQL |
| Autenticação | **JWT em cookie httpOnly** (`procar_token`), assinado com `JWT_SECRET` (HS256 fixo), exp curto (30 min) e **renovado de forma deslizante** pelo heartbeat enquanto há atividade, até um **teto absoluto de 12 h** por sessão. Validação bcrypt no login; middleware verifica o token, relê o usuário (revoga inativo na hora) **e valida a sessão em `sessoes`** — logout, troca e reset de senha marcam `encerrada_em` e derrubam o token na hora. Perfis `consultor`/`gestor`/`admin` (TI). Sessão **efêmera** (cookie de sessão → morre ao fechar o navegador) + **expira por inatividade** (30 min, `AuthContext`). **CSRF** por double-submit token (`procar_csrf` + header `X-CSRF-Token`). **Primeiro acesso** obrigatório (troca da senha temporária) via `usuarios.senha_definida`, **sem exceção de perfil** — inclusive o Admin — também reaproveitado pelo **reset de senha** (Admin reseta qualquer um; Gestor só consultores da própria loja). Throttle de login + **rate limit** global por IP e por usuário nas rotas sensíveis (tudo em memória). |
| Hospedagem | Servidor local PROCAR ou VPS Linux |

Diretrizes transversais:
- **Entrega incremental e modular** — cada módulo entregue funcional e testável antes do próximo; novos módulos plugam sem refatoração estrutural.
- Separação clara entre frontend e backend (API REST desacoplada).
- Priorizar componentes reutilizáveis e código limpo. **Não adicionar complexidade além do escopo do módulo em andamento.**

### ★ Guia de Atendimento — foco atual
Fluxo em **duas telas** (o atendimento vive só em memória — **nada é gravado no banco**):
1. **Wizard de atendimento** (tela inicial após login): no centro, o **nome da concessionária + logo SVG da marca** (admin vê "Novo atendimento"). Os campos aparecem **progressivamente** conforme o preenchimento, com **scroll suave até cada campo liberado**: **Cliente (nome) → Carro (só admin; concessionária tem marca fixa) → Modelo (com busca) → Cor → Bancos (tecido/couro) → Cor do couro (se couro) → Setor (select: Novos / Novos - Recém retirado / Seminovos / Oficina / Funilaria — lista em `SETORES`, guia.types.ts) → Canal (Presencial/Telefone — `CANAIS`)** → botão **"Gerar guia de atendimento"**.
2. **Guia gerado**: capa com o **nome do cliente** + veículo selecionado. O **conteúdo principal** é um único bloco — **"O que ofertar"** (seleção de serviços + Resumo Inteligente, ver **★ Resumo Inteligente** abaixo). Mais abaixo, em blocos **recolhíveis** (mesmo padrão para os três): **Contorno de objeções**, **Dicas de ouro** e o **Roteiro de atendimento completo** (texto original do manual, íntegro, em etapas numeradas — preservado para consulta detalhada, mas não é mais o conteúdo principal da tela). Botões **"+ Novo atendimento"** (capa) e **"Concluir e iniciar novo atendimento"** (rodapé) reiniciam o wizard.

### ★ Resumo Inteligente (dentro do Guia gerado)
Substituiu o card de "Resumo Rápido" (bullets: gancho/benefícios/momento ideal — texto autoral avulso, `servicos.resumo_rapido`, descontinuado) como conteúdo principal da tela. Agora:
- **Seletor de serviços** no topo: chips com **todos** os serviços do guia (não só os recomendados), roláveis horizontalmente no celular e em grade a partir do tablet. Os que casam com alguma `regra` para o atendimento atual ganham o selo **"★ Recomendado"**, borda em destaque e **prioridade na ordenação** (aparecem primeiro — o resto mantém a ordem de `servicos.ordem`).
- **Resumo Inteligente** (conteúdo principal): uma **narrativa contínua**, não uma lista de passos — texto único, fluido, pronto para o consultor ler antes de falar com o cliente. **Não é conteúdo novo/reescrito**: é a **combinação das mesmas etapas do roteiro** (já filtradas por setor/canal/banco e personalizadas por `montarRoteiro`/`personalizar`, ver `guia.engine.ts`), renderizadas como parágrafos sequenciais em vez de itens numerados com título — mais o **argumento do serviço selecionado** (`regras.argumento_template`, já com o valor real) como parágrafo de fechamento, quando há uma regra casada. Assim o texto já reúne cor (via `{argumento_cor}`), banco, setor/canal (que já filtram o roteiro) e o serviço recomendado, num só lugar — sem o consultor precisar cruzar informações entre blocos separados. Muda com a seleção de serviço (cada chip tem seu próprio fechamento).
- **Conteúdo dinâmico por serviço**: tocar num chip troca o Resumo Inteligente exibido — só o conteúdo daquele serviço aparece (o consultor não precisa rolar por todos).
- **Conteúdo original preservado**: abaixo do Resumo Inteligente, um bloco recolhível **"Conteúdo original do manual"** (mesmo padrão de Contorno de objeções/Dicas de ouro) mantém, na íntegra, a `descricao` original (preço/garantia) e — quando há uma `regra` casando com o atendimento — o `argumento_template` (o mesmo texto usado como fechamento do Resumo Inteligente, aqui isolado e rotulado como "Argumento de venda" para referência exata). Nada do conteúdo da empresa foi removido, só reorganizado.
- **Impressão ("Salvar em PDF")**: em tela, só o serviço selecionado fica visível; no papel, **todos os serviços** (com Resumo Inteligente + conteúdo original expandido) são impressos em sequência, e os três blocos recolhíveis do rodapé (objeções/dicas/roteiro completo) também são forçados abertos — o PDF continua sendo o resumo completo do atendimento.

> **Fonte do conteúdo:** o **Manual de Vendas PROCAR (V1/2026 — Setor de cuidado e proteção)** foi transcrito para o seed (`seed-guia.ts`): roteiros por setor/canal/banco, serviços com preços (Combo Full 6x 777, Coating de Pintura 6x 198 / Oficina 6x 335, Coating de Couro 6x 160, Impermeabilização 6x 93, Higienização 6x 93, bundle coating+bancos 6x 425), argumentos por cor, objeções e dicas. Adaptações: "Hugo/Corolla/Toyota/Karol" → `{cliente}`/`{modelo}`/`{fabricante}`/"(seu nome)". O **Resumo Inteligente** (§4) não introduz texto novo: é a recombinação das mesmas frases do roteiro em prosa contínua, mais o argumento do serviço em foco.

- **Visão por concessionária:** cada usuário pode ter uma `marca` (ex.: BMW) — o guia mostra **apenas os veículos daquela marca**; admin (`marca` NULL) vê todas as marcas principais. Usuários de teste (**só em desenvolvimento**, nunca semeados em produção): `bmw@procar.com.br`, `volkswagen@procar.com.br`, etc. (um por marca principal), cada um com **senha aleatória individual** exibida no terminal durante o `db:setup`.
- **Leve:** todo o conteúdo vem em uma chamada (`GET /api/guia/dados`, já filtrada pela marca do usuário), é cacheado no cliente (**chave por usuário**), e as recomendações são calculadas no frontend a partir das regras.

**Entregável:** o consultor preenche cliente + veículo e recebe, sem depender de rede, o roteiro do que falar e a lista do que ofertar — descartados ao concluir o atendimento.

### ★ Gerenciamento de usuários e reset de senha (Admin/Gestor)
Tela `/usuarios` (link no topo, visível a Gestor e Admin): lista os usuários dentro do escopo de quem está logado, com ações de **criar**, **editar**, **ativar/desativar**, **resetar senha** e — **só para Admin** — **excluir**. Um Gestor pode administrar **mais de uma loja** (concessionária) — não está limitado a uma só.

- **Admin (TI)**: vê/gerencia todos os Consultores e Gestores de todas as lojas (contas `admin` nunca aparecem nesta API). Único perfil que pode criar contas **Gestor**, mudar o perfil/loja(s) de um usuário existente ou **excluir** um usuário.
- **Exclusão (só Admin)**: remoção definitiva da conta, distinta de "Desativar" (que é reversível e preserva tudo). Leva junto, por cascata, o **histórico de uso** do usuário (`sessoes` e `atendimentos`) — as métricas do dashboard mudam retroativamente. **Não** apaga `reset_senha_log`: as FKs dessa tabela são `ON DELETE SET NULL` justamente para que excluir alguém não elimine a evidência de resets de senha (nem os que ele sofreu, nem os que executou em terceiros). Bloqueada para a própria conta e para contas `admin`. A UI confirma em modal próprio, avisando o que se perde e sugerindo "Desativar" quando a intenção é só bloquear o acesso.
- **Gestor**: pode administrar **uma ou mais lojas** (`usuario_marcas`, ver §6) — vê/gerencia apenas os **Consultores dessas lojas**. Ao criar um usuário, `perfil` é **forçado no servidor** (sempre `consultor`) e a `marca` deve ser uma das lojas que o gestor administra (se ele tiver só uma, ela é usada automaticamente; com mais de uma, o formulário pede para escolher em qual delas o novo consultor entra). Não pode alterar perfil, mover um consultor de loja, atribuir a si mesmo novas lojas, nem ver/tocar usuários de fora do seu conjunto de lojas (fora do escopo → `404`, não `403`, para não confirmar a existência da conta a quem não deveria vê-la). Pode trocar a **própria** senha a qualquer momento em "Minha senha" (rota `/minha-senha`, qualquer perfil exceto Admin).
- **Reset de senha**: reaproveita o mecanismo de **primeiro acesso** já existente — gera uma senha temporária aleatória (`xxxx-xxxx`, sem caracteres ambíguos), grava o hash e marca `senha_definida = 0`; a senha em texto puro volta **uma única vez** na resposta da API para quem executou o reset comunicar ao usuário (a UI mostra um aviso "não será exibida novamente"). No próximo login, o usuário cai obrigatoriamente em `/primeiro-acesso`. O reset também **encerra todas as sessões abertas do alvo** (`sessoes.encerrada_em`), expulsando na hora quem estiver com a conta — é o que faz o reset valer como resposta a um acesso indevido. Cada reset grava uma linha em `reset_senha_log` (quem resetou, quem foi afetado, quando) — só auditoria, sem PII adicional.

## 6. Domínio de Dados

### Veículos — importados da FIPE (tabelas `vehicle_*`, **dados externos, estrutura no `schema.sql`**)
`vehicle_brands`/`vehicle_models` são populadas a partir de `https://parallelum.com.br/fipe/api/v1` pelo script manual `backend/src/database/import-fipe/marcas-modelos.ts` (`npm run import:fipe:marcas` — ver [IMPORTACAO-FIPE.md](./IMPORTACAO-FIPE.md)). A **estrutura** dessas duas tabelas (`CREATE TABLE IF NOT EXISTS`, vazias) faz parte do `schema.sql`/`db:setup` desde 2026-07-31 — só isso, nenhuma chamada à FIPE no boot/setup. Os **dados** continuam vindo só do script manual, que roda depois do `db:setup`. `vehicle_years`/`vehicle_categories` continuam totalmente fora daqui (import opcional, ver IMPORTACAO-FIPE.md §6).
- **vehicle_brands** — `id, name` (+ `fipe_brand_id`). Marcas.
- **vehicle_models** — `id, brand_id (→ vehicle_brands), name, category, fipe_model_id, years_imported`. Modelos.
- **vehicle_years**, **vehicle_categories** — ⏳ ainda **não importadas** (e hoje nada no guia lê `vehicle_years`, mesmo havendo um script `import:fipe:anos` capaz de populá-la — deliberadamente fora do fluxo padrão de deploy, ver IMPORTACAO-FIPE.md §6). Enquanto `category` estiver vazia nos modelos, as regras por categoria (ex.: Picape) simplesmente não disparam (degradação suave).

> O guia exibe apenas as **marcas principais** — filtro em `backend/src/modules/guia/marcas-principais.ts` (casado por `name LIKE` contra `vehicle_brands`, cobrindo prefixos FIPE como "VW - VolksWagen").

### Conteúdo do guia — criado/semeado por este projeto (`schema.sql` + `seed-guia.ts`)
- **usuarios** — `id, nome, email (único), senha_hash, perfil ('consultor'|'gestor'|'admin'), marca (usada só por 'consultor': a loja onde atende, casada por LIKE contra vehicle_brands no guia; NULL para 'gestor'/'admin' — Gestor usa `usuario_marcas`, Admin não tem restrição), ultimo_login, senha_definida (0 = ainda usa a senha temporária/recém-resetada → primeiro acesso obrigatório; 1 = já trocou), ativo, created_at`. `admin` (TI) é o único perfil com acesso total; sua senha é trocada manualmente via SQL, sem fluxo no app.
- **usuario_marcas** — `usuario_id (FK usuarios), marca` (chave composta). Lojas administradas por um **Gestor** — pode ter **mais de uma linha por usuário** (um gestor multi-loja). Não é usada por Consultor (que tem uma única loja em `usuarios.marca`) nem Admin (sem restrição). Migração: gestores antigos com `usuarios.marca` preenchida (modelo de uma loja só) são migrados para cá automaticamente no `setup.ts`.
- **sessoes** — `id, usuario_id (FK usuarios), inicio, ultimo_visto, encerrada_em`. Uma linha por login; `ultimo_visto` avança via heartbeat enquanto o consultor está ativo. **Tempo logado = Σ(ultimo_visto − inicio)** — base do monitoramento do gestor. Também é a **autoridade da sessão**: o `sid` do JWT aponta para esta linha e o middleware a consulta a cada requisição — `encerrada_em` preenchida (logout, troca ou reset de senha) invalida o token na hora, e `inicio` mais velho que 12 h barra a renovação deslizante.
- **reset_senha_log** — `id, usuario_id (FK usuarios NULL, quem foi resetado), executado_por (FK usuarios NULL, quem executou), criado_em`. Auditoria leve do módulo `usuarios` (§4 — Gerenciamento de usuários): uma linha por reset de senha executado por Admin/Gestor. Sem PII além dos ids; a senha temporária gerada nunca é persistida em texto puro. As duas FKs são **`ON DELETE SET NULL`** (não CASCADE): excluir um usuário não pode apagar o registro de que o reset aconteceu — senão bastaria excluir o executor (ou a própria vítima) para eliminar a evidência. A linha sobrevive com o lado removido em `NULL`.
- **atendimentos** — `id, uuid (gerado no cliente, liga início↔conclusão offline), usuario_id (FK usuarios), sessao_id (FK sessoes), status ('iniciado'|'concluido'), marca, setor, canal, categoria, banco, iniciado_em, concluido_em`. Unicidade em **`(usuario_id, uuid)`** — não no `uuid` sozinho: como o uuid vem do cliente, uma chave global permitiria que a requisição de um usuário casasse no `ON DUPLICATE KEY` da linha de outro. **Auditoria de uso da ferramenta, SEM PII**: por construção não há coluna para nome/telefone/CPF/placa/chassi — só metadados não-identificáveis. Um registro por atendimento conduzido no guia (início na 1ª interação do wizard, conclusão ao gerar o guia). **Removido automaticamente após 60 dias** (retention job). Base das métricas de fichas iniciadas/concluídas do dashboard.
- **cores** — `id, nome, hex, argumento (texto de venda da cor — "Argumento por cores" do manual, injetado via {argumento_cor}), ordem, ativo`
- **servicos** — `id, nome, selo, descricao, ordem, ativo` (Combo Full de Proteção, Coating Cerâmico de Pintura (Q2 e CanCoat), Coating de Couro, Impermeabilização de Tecidos, Higienização Interna). `descricao` é o texto **original** do manual (preço/garantia), preservado. Não há mais um campo de resumo autoral avulso — o "Resumo Inteligente" (§4) é **calculado no frontend** a partir de `roteiro_etapas` + `regras.argumento_template`, não armazenado no banco (uma coluna `resumo_rapido` existiu brevemente e foi removida — ver §9).
- **roteiro_etapas** — `id, ordem, setor, canal ('presencial'|'telefone'), banco ('tecido'|'couro'), titulo, instrucao, frase_template` (campos `NULL` = etapa vale para qualquer atendimento; `instrucao` **e** `frase_template` aceitam `{cliente}` (alias `{nome}`), `{modelo}`, `{cor}`, `{fabricante}`, `{banco}`, `{cor_banco}`, `{setor}`, `{argumento_cor}`)
- **regras** — `id, ativo, prioridade, cor, categoria, modelo_id (opcional, → vehicle_models sem FK), banco ('tecido'|'couro'), setor, servico_id (FK servicos), argumento_template`
  - Oferece um **serviço** quando a seleção casa com `cor`/`categoria`/`modelo`/`banco`/`setor` (campos `NULL` = "qualquer"). `argumento_template` é o texto de venda com placeholders.
- **objecoes** — `id, tipo ('objecao'|'dica'), ordem, titulo, resposta, ativo` (contorno de objeções e dicas de ouro do manual; exibidos no guia como material de apoio, com placeholders personalizados)
- O **atendimento em si não é persistido** — cliente, veículo, bancos, setor e canal vivem só no estado do frontend durante o atendimento.
- `setup.ts` faz **migração leve** (adiciona `usuarios.marca`, `regras.banco`, `regras.setor`, `roteiro_etapas.setor/canal/banco`, `cores.argumento`, `sessoes.encerrada_em` se faltarem; alarga `instrucao` para TEXT; troca a chave única de `atendimentos.uuid` por `(usuario_id, uuid)`; amplia `usuarios.perfil` com `'admin'` e promove `admin@procar.com` a `admin`, se ainda não for; migra gestores com `usuarios.marca` legada para `usuario_marcas`) e semeia o admin. **Sem senha padrão:** o admin usa `ADMIN_SENHA_INICIAL` (obrigatória em produção; aleatória em dev) e nasce com `senha_definida = 0`, como qualquer outro perfil. As contas de concessionária são semeadas **só em desenvolvimento**, com senha aleatória individual.
- `seed-guia.ts` detecta o conteúdo do manual pelo serviço marcador ("Coating Cerâmico de Pintura (Q2 e CanCoat)"); se encontrar apenas o conteúdo antigo do MVP, **substitui** (regras/roteiro/serviços eram 100% seed — não há conteúdo editado pelo gestor até o P3 existir).

> Avaliação das regras é feita **no frontend** sobre os dados cacheados (§2). O backend apenas serve o conteúdo.

### Tabelas descontinuadas (não usadas)
`clientes`, `veiculos` e `fichas` (do antigo "fichário") **não são mais usadas** e foram removidas do `schema.sql` e do código. Se existirem no banco de uma versão anterior, podem ser ignoradas/removidas manualmente.

## 7. Contrato da API (guia)

- `GET /api/guia/dados` — retorna **todo o conteúdo do guia** em uma resposta (fabricantes com modelos aninhados — já filtrados pela(s) marca(s) do usuário: uma para Consultor, uma ou mais para Gestor, todas para Admin —, cores, serviços, roteiro e regras). É o único fetch necessário para o atendimento; o frontend cacheia e trabalha offline a partir daí.
- `POST /api/auth/login` — valida bcrypt, registra `ultimo_login`, abre `sessoes` e **seta o cookie httpOnly `procar_token`** (JWT, com `sid` = sessão) + cookie `procar_csrf`. Retorna `{ usuario, mustChangePassword }`. Throttle por e-mail+IP (429 ao exceder).
- `GET /api/auth/me` — restaura a sessão a partir do cookie (o token é httpOnly, o front não o lê): `{ usuario, mustChangePassword }`. 401 se não houver sessão válida.
- `POST /api/auth/senha` — (autenticado, **rate limit por usuário**) **primeiro acesso / troca de senha** `{ senhaAtual, novaSenha }` (política: ≥8, letra+número, ≠ atual); seta `senha_definida=1`, **encerra as demais sessões da conta** (preserva a corrente) e reemite o token. Disponível a **todos os perfis**, inclusive Admin.
- `POST /api/auth/logout` — **encerra a sessão no servidor** (`sessoes.encerrada_em`) e limpa os cookies. Limpar o cookie sozinho não invalidava uma cópia do token.
- `POST /api/auth/atividade` — heartbeat (sem corpo); avança `ultimo_visto` (a sessão vem do token) e **renova o cookie do token** (sessão deslizante). Chamado a cada 5 min **só quando houve atividade**; falha silenciosa offline.
- `POST /api/monitoramento/atendimento/iniciar` · `.../concluir` — (consultor) registram início/conclusão do atendimento com `{ uuid, marca?, setor?, canal?, categoria?, banco? }`. **Allowlist rígido — nenhum PII é aceito/persistido.** Fire-and-forget no front (offline-first). Usuário/sessão vêm do token.
- `GET /api/gestor/dashboard?dias=7|30|60` — (gestor) painel consolidado em **uma resposta**: KPIs (consultores ativos/sem uso recente, online agora, acessos hoje/período, fichas iniciadas/concluídas, taxa de conclusão), **série diária** (evolução) e **rankings** (mais usam / sem uso recente). Sem N+1.
- `GET /api/gestor/consultores?dias=&ordenar=&pagina=&limite=` — (gestor) lista **paginada** por consultor (métricas + status online + fichas), ordenável (mais usam / sem uso / nome).
- `GET /api/gestor/uso` — (gestor/admin) lista completa (compat.), online primeiro. A tela `/gestor/uso` faz **polling a cada 30 s** (só ela; não afeta o offline-first do atendimento).
- **Escopo das três rotas acima:** Gestor enxerga apenas os consultores das lojas que administra (`usuario_marcas`); Admin mantém a visão global. O escopo vem sempre do token, nunca da query.
- `GET /api/usuarios` — (admin/gestor) lista os usuários no escopo de quem pede: admin vê todos os consultores/gestores (contas `admin` nunca aparecem; gestores vêm com `marcas: string[]`); gestor só os consultores das lojas que administra.
- `GET /api/usuarios/marcas-disponiveis` — (admin/gestor) lista de lojas (`MARCAS_PRINCIPAIS`) para popular o formulário de criação/edição (seletor único p/ consultor, múltiplo p/ gestor).
- `POST /api/usuarios` — (admin/gestor, **rate limit por usuário**) cria um Consultor ou Gestor `{ nome, email, perfil?, marca?, marcas? }` (`marca` = loja única do consultor; `marcas` = uma ou mais lojas do gestor, só admin define). Gestor tem `perfil` **forçado no servidor** (sempre consultor) e `marca` validada contra as lojas que ele próprio administra (ignorando o que o corpo enviar fora desse conjunto). Gera uma senha temporária e responde `{ usuario, senhaTemporaria }` — a senha só aparece **nesta resposta**, uma vez.
- `DELETE /api/usuarios/:id` — (**só admin**, rate limit por usuário) exclusão definitiva. Barreira dupla: `authorize('admin')` na rota **e** checagem de perfil no service. Bloqueia a própria conta e contas `admin`; fora do escopo → `404`. Remove por cascata `sessoes`/`atendimentos`/`usuario_marcas` do alvo — e, como o middleware valida a sessão a cada requisição, quem estiver logado nessa conta perde o acesso na hora. `reset_senha_log` é preservado (SET NULL). Responde `204`.
- `PUT /api/usuarios/:id` — (admin/gestor) edita `{ nome?, email?, ativo?, perfil?, marca?, marcas? }`; `perfil`/`marca`/`marcas` só têm efeito quando quem chama é admin (`marcas` substitui o conjunto de lojas do gestor por completo). Fora do escopo de quem chama → `404`.
- `POST /api/usuarios/:id/resetar-senha` — (admin/gestor, **rate limit por usuário**) invalida a senha atual, marca `senha_definida=0` (reaproveita o primeiro acesso), **encerra todas as sessões abertas do alvo** e responde `{ usuario, senhaTemporaria }` (uma vez). Registra a ação em `reset_senha_log`. Não permite auto-reset (usar `/api/auth/senha`).

> **Transversal a toda a API:** headers de segurança em todas as respostas (`nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, HSTS quando há HTTPS), corpo JSON limitado a 100 KB e **rate limit global por IP** (600 req/min — dimensionado para uma loja inteira atrás de um NAT). Rotas que geram credenciais usam um limite adicional **por usuário** (30 a cada 15 min).

- **2026-07-31** — **Revisão de responsividade mobile-first (correção de bug relatado + consistência de breakpoints).**
  - **Bug relatado pelo cliente (print anexo):** na faixa fixa do topo (`AppHeader`), com muitos itens à direita (perfil gestor/admin: "Usuários", "Monitoramento", "Minha senha", tema, "Sair"), uma tela estreita não tinha espaço para tudo em uma linha só — os itens ficavam encavalados/ilegíveis, sobre a logo. Causa raiz: `.app-topo-in`/`.app-topo-dir` eram `display:flex` sem `flex-wrap`, então o conjunto de chips não tinha para onde ir. Corrigido com `flex-wrap: wrap` nos dois níveis (a logo fica na primeira linha; as ações quebram para uma 2ª linha quando não cabem, e entre si também quebram se necessário).
  - **Consequência resolvida junto (e regressão própria, corrigida na mesma sessão):** a faixa é `position: fixed`, e o espaço reservado abaixo dela (`padding-top` em `.guia`) vinha de uma constante CSS fixa (`--topo-altura: 60px`). Uma faixa que agora pode ter 2 linhas (mais alta que 60px) sobreporia o conteúdo da página, então `AppHeader.tsx` passou a medir a própria altura com `ResizeObserver` e escrever o valor real em `--topo-altura`. **Só que `.app-topo-in` também usava essa mesma variável como seu `min-height`** — um loop de realimentação (medir a altura de um elemento para definir a altura mínima desse MESMO elemento) fez a faixa crescer a cada ciclo até ficar enorme (centenas de pixels), reportado pelo cliente com print mostrando um vão gigante entre a faixa e o conteúdo logo após o primeiro deploy desta mudança. Corrigido separando as duas coisas: `.app-topo-in` volta a ter `min-height: 60px` fixo (constante de design, não a variável), e `--topo-altura` (escrita pelo `ResizeObserver`) passa a servir só para o `padding-top` das páginas — nunca mais realimenta o tamanho do próprio elemento medido.

  - **Estouro horizontal do Guia gerado no celular (bug PRÉ-EXISTENTE, não regressão desta sessão — relatado pelo cliente com print: textos e cartões cortados à direita).** Causa raiz: `.guia-bloco` (o bloco "O que ofertar") **nunca teve regra CSS base** — só uma de impressão.
